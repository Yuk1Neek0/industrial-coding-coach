## Prompt — paste into Claude Design

Build a **Challenge List Page** for a learning-coach web app, using
Next.js (App Router), React, TypeScript, Tailwind CSS, and shadcn/ui. It
is a single page at route `/repos/[owner]/[repo]/challenges`. Light and
dark mode. Use only mock sample data — do not add data fetching, API
calls, or a database; render from a typed in-file object so it is
trivial to swap for real server data later.

### Domain

The app coaches a job-seeking junior developer to genuinely understand
projects they built with heavy AI assistance. The user has imported one
of their GitHub repositories and a prior milestone (M6) has mapped how
the project actually works as a system — its architecture, key files,
request/data flow, state flow, AI-call flow, and a debug path. This
page is the entry point to **debug and expansion challenges** generated
from that map — small, realistic, project-tied tasks like "add a small
field", "trace a failed API call", "fix a schema mismatch", "add a
loading/error state", "add a unit test", "explain a broken CI result",
"extend one module safely".

Each challenge is generated by an AI call against the user's project
map and is **tied to specific files in their repo** — never generic.
The page is honest about that with a small "AI-generated challenges,
grounded in your project map" label, never hidden. Copy is plain,
calm, encouraging, jargon-light.

The page renders one list of **challenge list entries** for one
imported repo's snapshot. Each entry has this shape (typed challenge
shape per FR-3 + the latest-outcome shape per R4 / R5 mirroring the M8
grading shape):

```ts
type ChallengeType =
  | "add-small-field"
  | "trace-failed-api-call"
  | "fix-schema-mismatch"
  | "add-loading-error-state"
  | "add-unit-test"
  | "explain-broken-ci"
  | "extend-module-safely";

interface ChallengeListEntry {
  challengeId: number | null;     // null = applicable type, no row generated yet
  type: ChallengeType;
  typeLabel: string;              // plain-language label, e.g. "Add a small field"
  taskSummary: string | null;     // one-line summary of the task; null when not yet generated
  targetFiles: string[];          // in-scope files from the M6 project map (real paths)
  latestOutcome: LatestOutcome | null;  // user's latest attempt; null = not attempted
  generatedAt: Date | null;       // null when not yet generated
}

interface LatestOutcome {
  score: number;                  // 0–100 numeric score
  scoreBand: string;              // calm short label, e.g. "Solid grasp", "Getting there", "Needs review"
  passed: boolean;                // met the shared M8/M9 pass threshold
  attemptedAt: Date;              // "Last attempt <time>"
}

interface ChallengeListPageData {
  repo: { owner: string; name: string };
  ref: string;                    // imported snapshot ref, e.g. "main"
  entries: ChallengeListEntry[];
}
```

**Critical content rule — applicability:**

- The `entries` array contains **only types that apply** to this
  snapshot. Types that do not apply are **omitted, not faked**: no
  greyed-out row, no "coming soon", no synthesized placeholder. In
  particular, `explain-broken-ci` is omitted unless the snapshot
  exposes a real failing CI run or log — never invented from a CI
  config file.
- A row whose `targetFiles` would be empty (a generic challenge with
  no file reference) is **not in the list**. Every visible row names
  real file/module paths from the project map.

**Mock data — seed one realistic scenario:** a small AI-built Next.js
+ Drizzle + SQLite portfolio app (e.g. `mia-dev/portfolio-api`,
`ref: "main"`) with **5–6 entries** across at least four different
types. Mix the states:

- 1 row that is **applicable, generated, not attempted** (`latestOutcome` null).
- 1 row that is **applicable, generated, attempted with a passing
  score** (e.g. score 82, "Solid grasp", attempted yesterday).
- 1 row that is **applicable, generated, attempted with a low score**
  (e.g. score 41, "Needs review", attempted last week) — to show the
  honest, calm "needs review" presentation.
- 1 row that is **applicable, not yet generated** (`challengeId: null`,
  `taskSummary: null`, `generatedAt: null`) — with `targetFiles` still
  populated from the project map.
- Use realistic `targetFiles` paths (e.g.
  `apps/web/app/api/sessions/route.ts`,
  `packages/db/src/sessions/schema.ts`,
  `apps/web/app/(authed)/sessions/page.tsx`).
- **Do not include** an `explain-broken-ci` row — this scenario's repo
  has no real failing CI run.
- Write plausible `taskSummary` content — no "lorem ipsum".

### Page layout — route `/repos/[owner]/[repo]/challenges`

A single readable column (comfortable max width). From top to bottom:

1. A **page header**: `{owner}/{name}` as an `<h1>`; the `ref` as a
   `Badge` next to it; a one-line description: "Project-tied debug and
   extension challenges generated from your project map."; and a
   small, honest **"AI-generated challenges, grounded in your project
   map"** badge/label (real text, calm styling — not icon-only).
2. A quiet **map link**: "Based on the map of {owner}/{name} →"
   linking to `/map/{owner}/{name}`.
3. An optional **type filter** — render only when `entries.length >= 3`
   distinct types. A segmented control / `Tabs` / `Select` listing
   each applicable `typeLabel` plus an "All" option. Default "All".
   Filters the list client-side. **The filter only ever shows types
   present in `entries`** — types that don't apply must not be
   options.
4. The **challenge list** — one entry per `ChallengeListEntry`,
   rendered as a list of rows or cards (a shadcn `Card` per row works
   well). Each row shows:
   - the **`typeLabel`** as the row title (`<h2>` or `<h3>` per the
     heading order rule below);
   - the **`taskSummary`** as plain-language body text directly under
     the title; when `taskSummary` is `null` (and `challengeId` is
     `null`), show a placeholder instead: "Generate the first
     challenge of this type" — same row layout, calmer styling,
     obviously inviting the click;
   - the **`targetFiles`** as a wrapped row of monospace `Badge`-style
     chips (one per path); long lists wrap, never truncated to hide
     meaning;
   - the **latest-outcome status** (see below) on the right or below
     the body on narrow screens;
   - a quiet **"Generated {generatedAt}"** muted meta line (or
     "Not yet generated" when `generatedAt` is `null`).
   The row is a real **link** (or wraps exactly one link covering it)
   pointing to the Challenge Detail Page. When `challengeId` is set
   the destination is `/repos/{owner}/{name}/challenges/{challengeId}`;
   when `challengeId` is `null` (applicable, not yet generated) the
   destination is `/repos/{owner}/{name}/challenges/new?type={type}` —
   the Detail Page is where generation is actually triggered.
5. A quiet **footnote** below the list: "Each challenge is generated
   on first open, then cached per repository snapshot." Informational,
   not a link.

#### Latest-outcome status — per row

This is the row's "current status". It carries the user's **latest**
attempt (most recent, not first, not best — R5) — a 0–100 numeric
score (R4) and a calm short band label. Two visual states:

- **`latestOutcome` is `null`** → render "Not attempted" as a quiet
  neutral `Badge`. Calm, neutral styling.
- **`latestOutcome` is populated** → render a small status block:
  - the **`score`** (e.g. "82 / 100") as the prominent number;
  - the **`scoreBand`** as the short calm label (e.g. "Solid grasp",
    "Getting there", "Needs review") — text, not color alone;
  - a "Last attempt {attemptedAt}" muted line.

Convey meaning by **text** — no green-checkmark / red-cross only, no
color-only band. The same status component can also note `passed`
with a small honest "passed" / "below pass" text label, but the score
and band are the primary information.

### States — design all of these

Provide simple toggles or separate preview screens so all of these can
be viewed:

- **Populated** — the typical list above with 5–6 mixed-state rows.
- **Filtered** — with a type filter applied, the matching subset plus
  a "showing N of M" count line.
- **No filter matches** — when the filter excludes everything, keep
  the filter bar visible and show an inline "No challenges match this
  filter" message with a **Clear filter** button that resets it.
  Visibly distinct from "no applicable challenges" below.
- **Empty — no applicable challenges** — when `entries` is empty,
  render a calm panel: heading "No applicable challenges for this
  snapshot yet", a short explanation that challenges are only
  generated where the project map yields target files (and that
  "explain a broken CI result" needs a real failing CI run — *do not*
  fake it from a CI config file), and a secondary "View project map"
  link. This is a resting state, not an error.
- **Loading** — a skeleton view (shadcn `Skeleton`): a header bar,
  several row placeholders (each a title bar + path-chip bar + status
  block + meta line). The list view never shows an LLM-in-progress
  spinner — generation happens on the Detail Page, not here.
- **Error — repo not imported** — heading "This repository isn't
  imported yet", a short line, and an "Import this repository" action
  link to `/import`. No stack traces.
- **Error — no project map yet** — heading "No project map yet for
  this snapshot", a short line, and a "Map this project" action link
  to `/map/{owner}/{name}`. No stack traces.
- **Error — load failed** — a friendly error block: heading
  "Couldn't load challenges", a short explanation, and a "Try again"
  button. No stack traces.

### Visual & accessibility requirements

- Clean, modern, content-first design. Generous spacing, readable
  typography, calm and trustworthy — a learning tool, not a marketing
  page.
- Fully responsive: comfortable on mobile and desktop. The path-chip
  row wraps; the status block reflows below the body on narrow
  viewports.
- Light and dark mode, using shadcn/Tailwind theme tokens (no
  hard-coded colors).
- Use **lucide-react** icons (e.g. `arrow-left`, `map`, `file`,
  `play`, `check-circle`, `circle-help`).
- Semantic HTML: exactly one `<h1>` per page (the `owner/repo`
  title); the optional type filter sits in a `<nav>` or labelled
  region; the challenge list is a `<ul>`/`<li>` list (or a list of
  `<article>`s) under the main heading; row titles are `<h2>` (or
  `<h3>` inside `<article>`s — heading order must descend without
  skipping). `<main>`, `<nav>`, `<section>` landmarks used.
- **Row links** — each row is a real link (or contains exactly one
  link covering the row) with an accessible name that includes the
  `typeLabel`, the `taskSummary` (when present), and the latest-
  outcome status, so a screen reader user knows the row's identity
  and state without parsing chips.
- **Path chips** — file paths inside chips are `<code>`; the chip's
  accessible name names the path. Long lists wrap.
- **Status conveys meaning by text** — "Not attempted", the score,
  the band, and the passed/below-pass label are real text. No color-
  only or icon-only signals. All badges meet WCAG 2.1 AA contrast in
  both themes.
- **Type filter** is a labelled, keyboard-operable control (`Tabs`
  with a visible legend, a segmented control with an `aria-label`,
  or a `Select` with an `<label>`); the filtered-count line and the
  "no matches" message are real text.
- **AI-generated label** — the "AI-generated challenges, grounded in
  your project map" framing is real, announced text — not a
  color-only or icon-only signal.
- **Loading state** — skeletons are decorative and `aria-hidden`; the
  loading region carries `aria-busy="true"`.
- **Keyboard** — full keyboard operability with a visible focus ring:
  the map link, the (optional) filter control, every row link in
  order, and the empty-state / error-state actions are reachable;
  Enter/Space activate. DOM order = visual order.

### Components to use

shadcn/ui: `Card` (`CardHeader`, `CardTitle`, `CardDescription`,
`CardContent`), `Badge`, `Button`, `Skeleton`, `Separator`,
`Tabs` (or a segmented control / `Select`) for the type filter.
lucide-react for icons. Keep components small and composable so they
integrate cleanly into an existing shadcn/ui monorepo — reuse
`packages/ui` rather than duplicating primitives.
