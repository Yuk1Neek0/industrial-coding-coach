# Task: Instrument the M7/M9/M10 bounded calls

## Description

Wire the observed client (task 4) + `recordEval` into the existing bounded SDK
calls so they emit traces + evals in production, with **zero behavior change**
(NFR). Each call swaps `createLlmClient()` → `createObservedLlmClient(...)` and
adds one `recordEval(...)` after its existing integrity check.

## Acceptance Criteria
- [ ] M7 (learning-unit generate + grade), M9 (challenge generation + grading),
      and M10 (interview-Q&A + résumé-bullets) construct the observed client with
      a stable `traceName` per call and the call's `snapshotId`.
- [ ] After each call's existing integrity check runs, a `recordEval(...)` records
      the pass/fail + check name (reusing the existing check — **no new LLM call**).
- [ ] **Zero behavior change:** the calls return the same results in the same
      order; their existing test suites stay green unchanged.
- [ ] A test asserts that running an instrumented call writes a trace + eval; and
      that a forced observability-write failure does not change the call's result
      (non-blocking, via the task-4 guarantee).
- [ ] Where a call injects its client for tests, the observed wrapper stays
      injectable so existing mocked-transport tests keep working with no API key.

## Technical Details
- Edits the shipped bounded calls under `learning-units/`, `challenges/`,
  `learning-memories/` (+ their tests). No other task touches these files →
  parallel-safe, but this is the one task that touches the core LLM path: keep the
  diff minimal (client construction + one recordEval per call).
- Reuse each call's existing integrity-check result for the eval; do not duplicate
  the check.
- The observed client is best-effort (task 4), so a DB-less context (build/tests
  without the observability DB) must not break the call — verify.

## Dependencies
- 4 (observed client + recordEval).
