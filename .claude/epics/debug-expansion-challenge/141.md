# Task: File-reference integrity check module + tests

## Description

Build the file-reference integrity check module used by both the M9
generation call (task 003) and the M9 grading call (task 004). It rejects
any in-scope, out-of-scope, or grading-output file reference that is not
in the M6 project map for the snapshot (R8 + FR-6). This is the
project-grounding guard that keeps M9 honest: generic exercises whose
file references don't resolve to a real M6-named path are a failure mode,
not a fallback (PRD NFR "Project-grounded, never generic.").

## Acceptance Criteria
- [ ] Typed module under `packages/db/src/challenges/integrity-check.ts`
      (or sibling location next to the M9 data-access layer) exposes a
      single integrity-check function that takes (a) a candidate
      challenge or grading output, and (b) the M6 project map for the
      snapshot, and returns either a success or a typed rejection naming
      the offending reference(s).
- [ ] The check validates every file/module reference in: the challenge's
      in-scope set, the challenge's out-of-scope set, every per-criterion
      result in grading output, and every file reference in feedback
      prose — against the M6 project-map-named files only (R8).
- [ ] The check does **not** infer adjacent files (test files, type
      files, index files): a path is accepted iff the M6 project map
      explicitly names it (R8 / FR-3).
- [ ] The check is shared: task 003 calls it on every generated
      challenge before persisting; task 004 calls it on every grading
      output before persisting (FR-6).
- [ ] Tests cover: a valid challenge with all references in the M6 map;
      a challenge with one out-of-scope reference rejected; a challenge
      with an adjacent-but-unmapped file rejected; a grading output with
      a fabricated file reference rejected; an empty / minimal map
      handled gracefully.
- [ ] `pnpm typecheck` and `pnpm test` pass with no API key set.

## Technical Details

This task is the M9 analogue of the project-logic-mapper integrity check
(`.claude/epics/archived/project-logic-mapper/106.md`), but the
authoritative set is the **M6 project map** rather than the raw
snapshot file tree — the project map is the narrower, intentional set
of files M6 named, and R8 binds M9 to that narrower set.

The module is implemented independently of the SDK calls and lives in a
shared location so both task 003 and task 004 can import it without
cycles. It depends only on the M6 project-map data-access layer
(shipped) — no new map-access path, no new snapshot-access path
(ADR 0009, R7).

Reuses the test posture of the project-logic-mapper integrity check:
fixtures for a small synthetic project map and a small synthetic
challenge / grading output. No live API or GitHub calls in CI.
