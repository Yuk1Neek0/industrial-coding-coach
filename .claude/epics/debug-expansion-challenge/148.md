# Task: Integrate M9 UI into apps/web (final integration task)

## Description

Integrate the four M9 UI pieces — Challenge List Page, Challenge Detail
Page (with inline collapsible prior-attempts panel per R5), Debug
Walkthrough UI, and Completion Review UI — into `apps/web` and wire
them to the generation call (task 003), the grading call (task 004),
and the M9 data-access layer (task 001). End-to-end on a sample
imported repo with an existing M6 project map and an M11 snapshot:
list challenges → open a challenge → submit an explanation → receive a
0–100 score + weak-area breakdown → see the attempt history. No live
API or GitHub calls in CI.

## Acceptance Criteria
- [ ] Challenge List Page integrated into `apps/web` at route
      `apps/web/app/repos/[owner]/[repo]/challenges/page.tsx`,
      rendering the typed challenge list from task 001's data-access
      layer; entries name target file(s) / module(s) from the M6
      project map (US-1); types not applicable to the snapshot are
      omitted (R1 / R6); each entry surfaces the user's latest
      outcome (R5).
- [ ] Challenge Detail Page integrated into `apps/web` at route
      `apps/web/app/repos/[owner]/[repo]/challenges/[challengeId]/page.tsx`,
      rendering type / task description / in-scope / out-of-scope /
      acceptance criteria; **the inline collapsible prior-attempts
      panel** (R5 / FR-10) renders the latest attempt as primary and
      prior attempts inline collapsed; a "new challenge" action
      wires to task 003's regeneration path (R2).
- [ ] Debug Walkthrough UI integrated (inline on the Detail Page or on
      a sub-route, per task 006's resolution); a free-text explanation
      and optional per-file snippets (paths drawn from the M6 map per
      R8) submit through task 001's data-access layer; submission is
      persisted server-side and readable back (US-3 / FR-4); the
      "explanation only" framing (R3) is visible to the user.
- [ ] Completion Review UI integrated (inline on the Detail Page or
      on a sub-route, per task 006's resolution); renders the 0–100
      score (R4), per-criterion result, weak-area breakdown matching
      M8 (R4), and a short feedback paragraph (FR-5); every
      file/module reference resolves to a real M6-named path (R8 /
      FR-6); the page does not claim "this passes" (FR-7).
- [ ] Lazy-per-type generation behavior is honored end-to-end (R2):
      opening a challenge category for the first time triggers task
      003's generation; subsequent opens read the cached row from
      `challenges`; the "new challenge" action explicitly re-invokes
      generation.
- [ ] Multiple attempts on the same challenge persist (US-6); the
      latest attempt becomes the challenge's current status; prior
      attempts remain readable through the inline collapsible panel.
- [ ] Integration notes under
      `docs/design/ui-integration-notes/challenge-list-page.md`,
      `docs/design/ui-integration-notes/challenge-detail-page.md`,
      `docs/design/ui-integration-notes/debug-walkthrough-ui.md`, and
      `docs/design/ui-integration-notes/completion-review-ui.md`
      record any deviations from the Page Specs / Claude Design
      drafts (ADR 0007).
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm build`, `pnpm test` pass
      with **no API key set** (mocked / recorded SDK responses; no
      live API or GitHub calls in CI).

## Technical Details

Build from the task-005 / 006 / 007 / 008 Page Specs and the Claude
Design drafts produced from their prompts. Per ADR 0007, integration
notes for each page land under `docs/design/ui-integration-notes/` to
record any deviations (this is the M9 analogue of the M6 / M8
integration notes; see `.claude/epics/archived/diff-review/116.md`
and `.claude/epics/archived/project-logic-mapper/108.md`).

The integration touches **only**: routes under
`apps/web/app/repos/[owner]/[repo]/challenges/`, server-side
functions that call task 001's data-access layer, and the wiring
into task 003's generation call and task 004's grading call. It
does **not** introduce a new GitHub access path (ADR 0009), a new
project-map access path (R7), a new SDK wrapper (ADR 0005), or a
new database (ADR 0006).

The "explain a broken CI result" type is gated server-side at task
003's type-selection step (R6); the List Page simply renders the
types task 003 produced. The UI does not need to know how the
gating works.

This task runs on the same `epic/debug-expansion-challenge` branch
/ worktree (ADR 0008). Routing additions to `apps/web` are
additive; if M10 begins in parallel, coordinate at merge time.
