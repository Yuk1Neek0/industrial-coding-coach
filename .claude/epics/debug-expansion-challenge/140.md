# Task: challenges + challenge_attempts schema + Drizzle migration + data-access layer

## Description

Add two new tables — `challenges` and `challenge_attempts` — to the existing
SQLite database (ADR 0006) to persist M9's generated challenges and the user's
attempts on them. Generate the Drizzle migration, build a typed data-access
layer to create/read challenges, create/read attempts, and retrieve a
challenge's latest outcome, and ship tests. No new database, no new GitHub
access path, no new map-access path (per ADR 0006, ADR 0009, FR-8, FR-9).

## Acceptance Criteria
- [ ] `challenges` table defined in `packages/db/src/schema.ts`, keyed by

      columns covering the typed challenge model (FR-3): type, task
      description, in-scope file set, out-of-scope file set, acceptance

- [ ] `pnpm typecheck` and `pnpm test` pass with no API key set.

## Technical Details

Follow the existing table conventions in `packages/db/src/schema.ts` (see
`stack_explanations` and `diff_reviews` for the JSON column pattern). Per
ADR 0006, M9 adds tables — it does not introduce a new database.

The `challenges` row keys on snapshot identity plus challenge type / id so
that R2's lazy-per-type, cached-per-snapshot generation can look up an
existing row before issuing a new SDK call. The `challenge_attempts` row
keys on challenge id with a timestamp so multiple attempts per challenge
(US-6) are preserved and the latest-outcome accessor returns the most
recent attempt's grading result.

The data-access module lives under `packages/db/src/challenges/` and
mirrors the `stack_explanations` and project-maps data-access patterns
(see `.claude/epics/archived/project-logic-mapper/106.md`). It is the
single server-side surface used by `apps/web` and by tasks 003 / 004 /
009 — there is no second path to these tables.

Migration numbering is resolved at epic merge time; coordinate with any
parallel epic that also adds tables.
