# Task: Grading SDK call (0–100, M8-shape, explanation-only) + mocked tests

## Description

Build the second bounded Anthropic SDK call (per ADR 0005) that grades a
user's submission against a challenge's acceptance criteria and against
the M6 project map. Grading is over the user's **explanation only** —
which files they say they would change and why; optional snippets are
illustrative and **not graded** for style, naming, or plausibility
(R3 / FR-7). Output is a structured **0–100 numeric score plus a
weak-area breakdown** matching M8's grading shape (R4 / FR-5), with
per-criterion results and a short feedback paragraph. The pass
threshold and the weak-area schema are reused from M8 so the product
has one comprehension-grading pattern across M8 and M9. Every grading
output passes the task-002 integrity check before persisting (FR-6).

## Acceptance Criteria
- [ ] A bounded Anthropic SDK call on the shared `llm-foundation` client
      (ADR 0005) takes a challenge plus a user attempt
      (`challenge_attempts` row, free-text explanation, optional
      per-file snippets) and produces a typed grading result: 0–100
      numeric score, per-criterion results, a weak-area breakdown that
      **mirrors M8's grading shape** (R4), and a short feedback
      paragraph (FR-5).
- [ ] The grader scores **the user's explanation only** — never the
      snippet content for style / naming / plausibility (R3 / FR-7).
      Widening this boundary would require a new ADR; this task does
      not widen it.
- [ ] The pass threshold and the weak-area schema match M8's
      (`packages/db/src/diff-reviews/` grading output) — reused, not
      reinvented (R4 / FR-5).
- [ ] Every grading output passes the task-002 integrity check before
      persisting via the task-001 data-access layer: every file/module
      reference in per-criterion results and feedback resolves to a
      file the M6 project map names (R8 / FR-6).
- [ ] The grading result is persisted on the corresponding
      `challenge_attempts` row (task 001's data-access layer); multiple
      attempts per challenge (US-6) each carry their own grading
      result, and the latest outcome is the one surfaced as the
      challenge's current status.
- [ ] The grader degrades gracefully on very short, empty, or
      off-topic submissions: it returns a low score with clear feedback
      and does not crash (PRD NFR "Resilient").
- [ ] Does **not** execute, build, lint, or test the user's code
      (FR-7); the grader does not claim "this passes."
- [ ] Tested with mocked / recorded SDK responses per the
      `llm-foundation` test strategy: a passing submission, a partial
      submission, an empty submission, a submission with an
      off-project file reference rejected by the integrity check, and
      a multi-attempt sequence persisting each grading result. CI
      makes no live API or GitHub calls.
- [ ] `pnpm typecheck` and `pnpm test` pass with no API key set.

## Technical Details

Per ADR 0005, the grading call is a separate bounded Anthropic SDK
call from the generation call (task 003) — generation and grading are
distinct, so the challenge shape is fixed before any answer is graded
and grading is reproducible with mocked / recorded SDK responses. This
mirrors M8's two-call separation
(`.claude/epics/archived/diff-review/113.md`).

The grader lives in a new module — for example
`packages/db/src/challenges/grading.ts` (or the corresponding
location alongside the `llm-foundation` consumers). The weak-area
schema, pass threshold, and per-criterion shape are imported from /
parallel to the M8 grading module rather than redefined (R4).

The grading call writes back into `challenge_attempts.grading_result`
via the task-001 data-access layer. Because task 003 also writes into
the same data-access module's mutation surface (for caching generated
challenges), tasks 003 and 004 are listed in each other's
`conflicts_with` — they cannot run in parallel.

The grader **does not** execute, build, lint, or test user code
(FR-7). The grader **does not** read the user's repository over a
new GitHub path (ADR 0009): it reads the M11 snapshot through the
shipped snapshot data-access layer only.
