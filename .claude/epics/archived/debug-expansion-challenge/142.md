# Task: Generation SDK call (lazy-per-type, cached) + mocked tests

## Description

Build the bounded Anthropic SDK call (per ADR 0005) that generates a
project-tied challenge from the M6 project map and the M11 snapshot. The
call is **lazy, per challenge type, on first open of that category**, and
generated challenges are **cached per snapshot** in the `challenges`
table so subsequent opens do not re-call the SDK (R2 / FR-1). The
"new challenge" action re-invokes generation for the same type. The call
produces **at least one challenge per applicable challenge type** (R1 /
FR-1, FR-2). Output is integrity-checked against the M6 project map
(R8 / FR-6) before persisting. Tested with mocked / recorded SDK
responses per the `llm-foundation` test strategy — no live API calls in
CI.

## Acceptance Criteria
- [ ] A bounded Anthropic SDK call on the shared `llm-foundation` client
      (ADR 0005) produces a typed challenge: type, plain-language task
      description, in-scope file/module set, out-of-scope file/module
      set, acceptance criteria, source references into the M6 project
      map (FR-1, FR-3). Tool use reads specific snapshot files where
      needed; this is a bounded call, not an autonomous agent.
- [ ] Lazy-per-type, cached-per-snapshot behavior: on first open of a
      challenge category for a snapshot, the call runs and the result
      is persisted via the task-001 data-access layer; on subsequent
      opens, the cached row is returned and the SDK is **not**
      re-called (R2). A "new challenge" action explicitly re-invokes
      generation for the same type.
- [ ] At least one challenge per applicable challenge type is produced
      for a sample repo (R1, FR-2). Types that do not apply to the
      snapshot are skipped, not faked.
- [ ] The "explain a broken CI result" type is gated at the
      type-selection step: it is emitted only if the M11 snapshot
      exposes a real failing CI run / log (R6 / FR-2). Until M11
      surfaces those, the type is omitted, not synthesized from a CI
      config file. **The gating logic lives inside this task's
      type-selection step (a few lines on top of the broader selection),
      not as a separate task.**
- [ ] Every generated challenge passes the task-002 integrity check
      before persisting; rejected outputs are not silently swallowed
      (R8 / FR-6).
- [ ] In-scope and out-of-scope file sets are strictly limited to files
      the M6 project map explicitly names — no adjacent-file inference
      (R8 / FR-3).
- [ ] Tested with mocked / recorded SDK responses per the
      `llm-foundation` test strategy: a successful generation per
      applicable type, a "new challenge" re-invocation, a cached-hit
      path that does not call the SDK, a broken-CI gating path with
      and without a real failing CI run, and an integrity-check
      rejection. CI makes no live API or GitHub calls.
- [ ] `pnpm typecheck` and `pnpm test` pass with no API key set.

## Technical Details

Per ADR 0005, M9 is two bounded Anthropic SDK calls on the shipped
`llm-foundation` client — **not LangChain**, **not an autonomous
agent**. LangChain remains confined to M6. The generation call mirrors
the M8 diff-review call pattern (see
`.claude/epics/archived/diff-review/112.md`): prompt → structured
output, tool use for file reads, mocked / recorded SDK responses for
tests.

The challenge generator lives in a new module — for example
`packages/db/src/challenges/generation.ts` (or the corresponding
location alongside the `llm-foundation` consumers). It depends on the
task-001 data-access layer to persist results and read cached rows, and
on the task-002 integrity check to validate output before persisting.
This creates a write path into `challenge_attempts.grading_result` only
in task 004, but both tasks 003 and 004 share the data-access module's
mutation surface; they are listed in each other's `conflicts_with` for
safety.

The broken-CI gating (R6) is a **few lines on top of the type-selection
step**: ask the M11 snapshot data-access layer whether a real failing
CI run is available; if not, drop the broken-CI type from the candidate
set before generation. The epic deliberately keeps this inside task
003 rather than spinning it off (epic's "Parallelization" note).

No new GitHub access path (ADR 0009): CI status is read through the
M11 snapshot data-access layer only. No new SDK wrapper (ADR 0005). No
new database (ADR 0006).
