# Task: CCPM artifact storage — schema + Drizzle migration

## Description

Add persistence for parsed CCPM artifacts and their issue/PR link annotations to
`packages/db/src/schema.ts`, plus a Drizzle migration. This is the storage layer
that the parser (002), linking (005), and data-access (007) tasks write to and
read from. Keying is per-snapshot (`owner/repo/ref`) so a re-import replaces the
prior artifact set in place, consistent with M11's `repo_snapshots`/`repo_files`
re-import semantics.

## Acceptance Criteria
- [ ] New table(s) store CCPM artifacts (type ∈ prd|epic|task), keyed to a
      `repo_snapshots` row, capturing: artifact type, repo-relative path, the
      parsed frontmatter fields needed downstream, and the markdown body.
- [ ] New storage for per-task issue/PR link annotations (issue state, closing
      PR identity/url, link-failure reason) keyed to the task artifact.
- [ ] A Drizzle migration is generated against current `main` head and applies
      cleanly; `pnpm --filter @repo/db build` + migration check pass.
- [ ] Re-importing the same `owner/repo/ref` replaces the prior artifacts/links
      (no orphan rows), mirroring M11's snapshot replacement in a transaction.
- [ ] Exported Drizzle types (`$inferSelect`/`$inferInsert`) for the new tables
      are added to the package surface, following the existing schema pattern.
- [ ] Schema-shape unit test added (mirrors `snapshot-schema.test.ts` /
      `learning-units-schema.test.ts`).

## Technical Details
- Edit only `packages/db/src/schema.ts` (+ generated migration + a new
  `*-schema.test.ts`). Do NOT touch `key-files.ts`/`import.ts` (task 003) or the
  new `ccpm/` modules (other tasks) — keeps Wave-1 parallelism conflict-free.
- Follow the existing table style in `schema.ts` (snake_case columns, `createdAt`/
  `updatedAt`, FK to `repo_snapshots.id` with cascade-on-delete to match
  `repo_files`).
- Store frontmatter as typed columns where stable (type, status, github,
  prd-ref, name/description) and the body as text; avoid over-modeling — the
  graph builder (004) derives edges from these fields.
- M12 runs solo (no parallel epic on `packages/db`), so migration numbering will
  not collide — still regenerate against the latest `main`.
