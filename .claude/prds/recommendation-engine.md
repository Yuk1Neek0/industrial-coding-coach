# PRD: recommendation-engine

## Executive Summary

Milestone 4. The Recommendation Engine takes a job-seeking junior dev's context
— goal, experience level, known stack, job target, time budget, complexity
tolerance, project type, AI-tool preference, learning focus — and recommends a
Golden Path plus a template set, with rejected alternatives and a coaching
narrative they can use to defend the choices in an interview.

It is **hybrid**: a deterministic, testable scoring layer ranks candidates
against the M2 catalog and M3 registry fit-data and decides the recommendation;
a bounded **Anthropic SDK** call (per ADR 0005) generates the human-facing
narrative — why each choice fits, complexity risks, learning checkpoints,
portfolio value. Results persist to the existing catalog SQLite database so they
are revisitable and human-editable. The intake and result UIs are produced
through the Claude Design round-trip (ADR 0007).

## Problem Statement

M2 delivered a Golden Path catalog and M3 a template registry, but nothing
connects them to an individual user. A junior dev looking at the catalog has no
guidance on which path or templates fit their goal, experience, and job target —
and no articulation of the trade-offs they would need to explain in an
interview.

A pure-LLM recommender would be unreproducible and could drift away from the
real catalog; a pure rules engine would rank defensibly but explain poorly. The
hybrid split keeps the decision deterministic and testable while using a bounded
LLM call for what it is good at — turning a ranked result into clear,
project-specific coaching prose. Per ADR 0005, that LLM call is the Anthropic
SDK directly, not an agent framework.

## User Stories

- **As a job-seeking junior dev**, I enter my context and receive a recommended
  Golden Path and template set ranked for me, citing real catalog entries.
  *Acceptance:* the result references `golden_paths` and `templates` by slug;
  the ranking is identical for identical input.

- **As a junior dev**, I see which alternatives were rejected and why.
  *Acceptance:* the result lists at least one rejected alternative with a
  concrete reason.

- **As a junior dev preparing for interviews**, I get a plain-language
  explanation of why each choice fits, the complexity risks, learning
  checkpoints, and the portfolio value of the project.
  *Acceptance:* the narrative is generated by a bounded Anthropic SDK call,
  cites the user's intake context, and references the recommended entries.

- **As a user**, I can review and edit a recommendation.
  *Acceptance:* a stored recommendation is editable and edits persist.

- **As a developer**, recommendations are saved and retrievable.
  *Acceptance:* a `recommendations` table stores the intake context and result;
  a typed data-access layer reads/writes it; tests cover it.

## Functional Requirements

- **FR-1 — Intake model.** A typed schema for the nine intake fields from the
  milestone plan (goal, experience level, known stack, job target, time budget,
  complexity tolerance, project type, AI-tool preference, learning focus).
- **FR-2 — Deterministic scoring.** A pure, unit-tested function scores each
  Golden Path and template against the intake using the M3 registry's
  structured fit-data and Golden Path metadata, producing a ranked
  recommendation plus rejected alternatives. Identical input yields an identical
  ranking.
- **FR-3 — Narrative generation.** A bounded Anthropic SDK call, built on the
  `llm-foundation` client, takes the scored result, the intake, and catalog data
  and produces a typed, structured narrative covering: why each choice fits,
  complexity risks, learning checkpoints, and portfolio value. It uses
  structured outputs and prompt caching; it is not an autonomous agent.
- **FR-4 — Catalog citation.** Every recommendation cites catalog entries
  (`golden_paths` and `templates` by slug); it never returns generic advice
  disconnected from the catalog.
- **FR-5 — Persistence.** A `recommendations` table, added via a Drizzle
  migration to the existing catalog SQLite database (ADR 0006), stores the
  intake context, the scored result, and the generated narrative — list-valued
  fields as JSON columns, matching the `golden_paths` / `templates` pattern. No
  new database.
- **FR-6 — Data-access layer.** A typed module to create, read, and update
  recommendations server-side from the Next.js app.
- **FR-7 — Human review and edit.** A stored recommendation can be edited by a
  human and the edit persists.
- **FR-8 — UI via Claude Design.** A Recommendation Intake page and a
  Recommendation Result page (surfacing the trade-off explanation and learning
  checkpoints), each preceded by a Page Spec under `docs/design/` and a prompt
  under `docs/design/ui-prompts/` before any Claude Design generation (ADR 0007).

## Non-Functional Requirements

- **Reproducible:** scoring is deterministic and unit-tested; the narrative call
  is tested with mocked SDK responses per the `llm-foundation` test strategy; CI
  makes no live API calls.
- **Referentially sound:** every recommendation reference resolves to a real
  catalog entry, proven by a referential-integrity test.
- **Non-duplicative:** reuses the M2 and M3 data-access layers and the
  `llm-foundation` client; no second catalog-access or SDK path.
- **Reviewable:** the recommendation is human-readable, editable, and
  inspectable — coaching, not a black box (on-thesis with ADR 0005).

## Success Criteria

- Given a sample intake, the engine returns a ranked Golden Path and templates
  citing real slugs, plus at least one rejected alternative with a reason.
- The narrative covers all four required output dimensions (fit, complexity
  risks, learning checkpoints, portfolio value) and references the intake.
- The `recommendations` table, its migration, and the data-access layer land
  with tests; the referential-integrity test passes.
- The Intake and Result pages are integrated into `apps/web` and wired to the
  engine.
- `pnpm lint`, `pnpm typecheck`, `pnpm build`, `pnpm test` all pass — with no
  API key set.

## Constraints & Assumptions

- The LLM mechanism is fixed by **ADR 0005**: the Anthropic SDK directly, not an
  agent framework, not LangChain.
- Depends on the `llm-foundation` epic; LLM work cannot begin until it lands.
- Reuses the existing catalog SQLite database (ADR 0006) — one new table, no new
  database.
- UI uses Claude Design (ADR 0007), only after page specs exist.
- Assumes M2's five Golden Paths and M3's fifteen templates are sufficient seed
  data to recommend over.

## Out of Scope

- The `llm-foundation` shared client (separate, prerequisite epic).
- M5 stack-decision explanation.
- Any agent framework or LangChain (ADR 0005 reserves agentic work for M6).
- User accounts, authentication, or saved multi-recommendation profiles.
- Recommendation history or versioning beyond a single editable record.
- ML-based ranking or re-scoring as the catalog grows.

## Dependencies

- **`llm-foundation`** epic — hard dependency for the narrative-generation task.
- **M2 `golden-path-catalog`** — `golden_paths` table and data-access layer
  (shipped).
- **M3 `template-registry`** — `templates` table, data-access layer, and
  structured fit-data (shipped).
- Governed by **ADR 0005** (LLM mechanism) and **ADR 0007** (UI tool).
- The existing `apps/web` Next.js app.
